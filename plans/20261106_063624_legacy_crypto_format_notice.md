# Plan: Warn when an old, weak encryption format is unlocked

**Status:** completed

## The issue

A security review flagged this (LOW): when the app reads old encrypted QR payloads, it
still accepts weak schemes:

- StegoQR v1 (`StegoQrService.decryptPayload` and `EncryptedPayloadService._decryptStegoQr`):
  AES-CBC, no tamper check, only 10,000 PBKDF2 rounds.
- JSON envelope (`EncryptedPayloadService._decryptJsonEnvelope`): when there is no salt, the key
  is plain SHA-256 of the passphrase. When the IV is not 12 bytes, it uses AES-CBC (no tamper check).
- Generic / custom ciphertext (`EncryptedPayloadService.decryptRaw`, also used by the manual
  decrypt sheet): key is always plain SHA-256 of the passphrase, and CBC may use an all-zero IV.

The weakness is inside the old files, so the reader cannot make them stronger. Refusing them
would only lock people out of their own data. What the app can do:

1. Tell the user honestly when content came from a weak, old format.
2. Make sure app code can never write the weak format.

A related finding: `StegoQrService.createStegoPayload` still **writes** StegoQR v1. Today only
tests call it, but it is public, so a future screen could use it by mistake.

## The fix

### 1. Mark legacy unlocks in the models (layer: `models`)

- `lib/models/encrypted_payload_data.dart`: add `final bool isLegacyFormat` (default `false`),
  plus the `copyWith` parameter.
- `lib/models/stego_qr_data.dart`: same field and `copyWith` parameter.

### 2. Set the flag in the services (layer: `services`)

- `lib/services/stego_qr_service.dart`
  - `decryptPayload`: on success set `isLegacyFormat: true` (v1 is the only StegoQR version).
  - `createStegoPayload`: add `@visibleForTesting` and a doc comment saying it writes the weak
    v1 format and must never be used by app code. Tests keep using it.
- `lib/services/encrypted_payload_service.dart`
  - `_decryptStegoQr`: on success set `isLegacyFormat: true`.
  - `_decryptJsonEnvelope`: on success set `isLegacyFormat: true` when there was no salt
    **or** the mode was CBC. GCM with a PBKDF2 salt stays `false`.
  - `_decryptGeneric`: on success set `isLegacyFormat: true`.
  - AirQR stays `false` (PBKDF2 200,000 rounds + AES-GCM).
  - No change to how decryption works. Old files still open exactly as before.

### 3. Show a notice (layer: `screens`)

- `lib/screens/result_screen.dart`
  - In the encrypted / StegoQR card: when unlocked and `isLegacyFormat` is true, show a small
    amber note row (warning icon + text) under the subtitle.
  - In the manual decrypt sheet: when a result is shown, show the same note (that path always
    uses the weak SHA-256 key).

### 4. New localized string

One new key, `bodyLegacyCryptoFormat` (a `body…` key, so long text is allowed):

### 5. Tests

- `test/services/stego_qr_service_test.dart`: unlocked v1 has `isLegacyFormat == true`.
- `test/services/encrypted_payload_service_test.dart`: StegoQR → `true`; JSON envelope without
  salt → `true`; JSON envelope with salt + 12-byte IV (GCM) → `false`; generic → `true`;
  failed unlock → `false`.
- `test/models/stego_qr_data_test.dart`: `copyWith` keeps and changes the new field.
- `test/screens/result_screen_test.dart`: the note shows for a legacy unlock and is hidden
  otherwise (if the existing test setup allows this without a large rewrite; if not, say so in
  the change log).

### 6. Docs

- `docs/security.md`: in the StegoQR / encrypted payload part, add one line: old formats are
  read only, are labelled in the UI as weak, and the app never writes them.
- `CHANGELOG.md`: one line under the next version.

## Not in this plan

- A new StegoQR v2 writer. The app has no StegoQR writer screen today, so there is nothing to
  write. If one is added later, it must use the `PassphraseCipher` scheme (PBKDF2 600,000 +
  random salt + AES-GCM) under a `STEGOQR:v2:` header.
- A setting to turn old formats off. Extra UI for little gain.
- Side note found while reading: the manual decrypt sheet sends a `salt` value, but `decryptRaw`
  ignores it. This is a separate bug; it can get its own plan.

## Security impact

No change to permissions, network, storage or dependencies. Decryption behaviour is unchanged;
the change only adds an honest warning and stops app code from writing the weak format.

## Checks after the change

`dart format .`, `flutter analyze` (zero warnings), `flutter test`, ARB key parity and the
Sanskrit Hindi-marker gate.
